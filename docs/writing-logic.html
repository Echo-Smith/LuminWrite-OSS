01 · Three Engines

三种执行引擎，统一风格注入

笔润智谈根据用户选择的 AgentMode 启动不同的执行引擎。三种引擎各有所长，但都通过同一套 RenderWritingConstraints 渲染风格约束，确保风格不漂移。

ENGINE · 01

Pipeline

agent_mode = pipeline

固定步骤流水线，每一步按预定义顺序执行，支持并行组和暂停恢复。

  • 意图分类 → 检索 → 提纲 → 写作 → 评审 → 修正
  • 支持 ParallelGroup（记忆 ∥ 搜索）
  • OutlineStep 可暂停等待用户确认
  • Agent Loop：搜索结果 ≥3 条时自动启用
ENGINE · 02

Harness

agent_mode = harness

单层 LLM 持续会话，LLM 自主决定调用什么工具、何时写作。WorldState 增量 diff。

  • 规则意图判定（毫秒级，不调 LLM）
  • WorldState 7 个 Section 增量推送
  • ChatWithTools 工具循环 + MaxCalls guard
  • 对话历史压缩 + 断线重连
ENGINE · 03

编辑部

agent_mode = editorial

DAG 工作流编排，研究→写作→审校三 Agent 协作，人类审批节点。

  • ResearchAgent → WritingAgent → ReviewAgent
  • RoleAgentRunner 角色化执行
  • 组织知识 + 栏目偏好注入
  • 交付物 Artifact 管理 + 事实核查
02 · Pipeline Flow

Pipeline 步骤流

Pipeline 模式按固定顺序执行步骤。意图分类后，非 writing 模式会跳过检索链；guided 模式在写作前生成提纲并等待用户确认。

Pipeline 执行流（writing + guided 模式）
灰色划线 = 非写作模式下跳过的步骤
ShortTermMemory→ Intent→
PARALLEL MemoryGate∥ QueryPlan→ Search→ Relevance→ Compress
→ WorkingMemory→ Chat (skip if not chat)→ Outline (guided only)→ Write→ PostReview→ AutoFix→ PostReview²→ MemoryExtract
polish/shorten/expand 模式：QueryPlan ✓ → Search ✗ → Relevance ✗ → Compress ✗ → Outline ✗ → Write ✓（不注入结构约束）
03 · Intent & Mode

意图分类 × 执行模式

意图（Intent）决定"做什么"，模式（Mode）决定"怎么做"。意图由 ClassifyIntent 规则判定或 LLM 分类；模式由前端传入 execCtx.Mode。

意图 触发关键词 检索 提纲 结构注入 Thinking 输出格式
写作writing 写一篇 / 写稿 / 撰写 / 基于热搜 ✓ guided 模式 ✓ 全量 ✓ high JSON标题 + 分隔符 + Markdown
润色polish 润色 / 优化 / 改写 / 调整 ✗ ✗ ✗ 不注入 ✓ 纯 Markdown
缩写shorten 缩写 / 精简 / 缩短 ✗ ✗ ✗ ✓ 纯 Markdown
扩写expand 扩写 / 展开 / 扩充 / 补充 ✗ ✗ ✗ ✓ 纯 Markdown
提炼extract_points 提炼 / 提取观点 / 提取要点 ✗ ✗ ✗ ✓ 结构化列表
对话chat 默认（无写作关键词） 可选 ✗ ✗ ✗ 纯文本流
关键设计决策：润色模式不注入结构约束。原因：润色是优化已有文本的表达，不应将一段文字强制变成结构鲜明的文章。结构约束仅在 taskMode == "writing" 时注入。
04 · Harness Flow

Harness 单层会话执行流

Harness 不走固定步骤，而是将工具集暴露给 LLM，由 LLM 在持续会话中自主决定调用顺序。WorldState 管理跨轮状态。

Run() 执行序列

1
加载对话历史 — 从 SessionStore 加载最近 50 条消息
2
主动检索记忆 — MemoryRetriever 接口注入用户偏好
3
意图判定 — ClassifyIntent() 规则路由，毫秒级
4
对话历史压缩 — 超阈值时 LLM 压缩旧消息为摘要
5
构建消息 — WorldState 7 Section 增量 diff → system prompt
6
选择工具集 — ToolsForIntent(intent, hasSearch, isGuided, hasKB)
7
构建执行器 — BuildToolExecutor + 声明式 MaxCalls guard
8
启动 LLM 会话 — ChatWithTools 或 ChatStreamWithReasoning
9
流式回调 — onDelta 提取标题 / onReset 保存正文 / onReasoning 推理链
10
收尾 — 保存文章版本、存储消息、发送 Completed 事件

06 · Structure Types

结构类型与自定义骨架

Structure.Type 决定文章的结构骨架。custom 类型通过 Sections 数组支持任意文体的自定义结构段，彻底解耦三段式硬编码。

type = three_part

三段式闭环

Opening → Body → Conclusion 三段，可附加论证模式和递进变式。适用于预设评论风格等评论文体。

开头→ 正文→ 结尾
opening: 现象点题 → body: 分层论述 → conclusion: 总结升华
type = free_form

自由结构

不预设结构骨架，由 LLM 根据话题自主决定段落组织。适用于杂文、随笔等灵活文体。

无固定段
结构要求由 LLM 自主决定
type = custom ⭐

自定义骨架

通过 Sections[] 数组定义任意结构段。每个段包含 Name 和可选 Description。适用于论文、公文、小说等任意文体。

引言→ 方法→ 实验→ 讨论→ 结论
sections: [{name:"引言",desc:"概述背景"},...]
结构骨架全链路感知：RenderStructureSkeleton() 在提纲生成阶段注入骨架引导，appendStructure() 在写作阶段注入结构约束，appendStructureSummary() 在评审阶段验证结构合规。

  // 1. 注入风格身份

10 · Decisions & Changes

架构决策记录与变更日志

以下记录本次重构中做出的关键设计决策和具体代码变更。每条决策包含背景、方案和影响范围。

D-01 架构

结构解耦：移除三段式硬编码，支持自定义 Sections

背景

原 Structure 类型硬编码 opening/body/conclusion 三段，无法表达论文（引言→方法→实验→讨论→结论）、公文、小说等文体的结构。用户自定义结构时，提纲生成和正文写作均无法感知。

方案
  • 新增 SectionPart 结构体（Name + Description）和 Structure.Sections []SectionPart 字段
  • 新增 type = "custom" 结构类型，通过 Sections 数组定义任意结构段
  • ValidateProfile 增加 custom 类型 Sections 非空校验
  • 新增 RenderStructureSkeleton() 为提纲生成注入结构骨架引导
  • appendStructure() 重构，custom 类型动态渲染 Sections 约束
影响文件
profile.go profile_prompt.go steps.go (OutlineStep) tools.go (generateOutlineWithLLM)
D-02 架构

引擎统一：三引擎共享 RenderWritingConstraints

背景

Pipeline、Harness、编辑部三引擎各自构建风格约束，存在风格漂移风险。Harness 模式提纲生成阶段缺少风格注入，导致自定义结构骨架不被感知。

方案
  • 确立 RenderWritingConstraints() 为风格约束单一真相源
  • 新增 RenderStructureSkeleton() 用于提纲阶段结构骨架注入
  • Harness generateOutlineWithLLM() 增加 p *profile.StyleProfile 参数
  • 两次调用（初始生成 + LLM 重写）均传入 cfg.Profile
  • Pipeline PromptBuilder.AddStyleConstraints() 确保调用 RenderWritingConstraints
  • 编辑部 RoleAgentRunner.buildSystemPrompt 复用统一渲染层
一致性矩阵

三引擎注入维度完全对齐：SystemPrompt ✓、FactGuard(P0) ✓、Structure(P1) ✓、Rhetoric(P1) ✓、WordRange(P1) ✓、ValueOrientation(P2) ✓

D-03 性能

搜索并发：Pipeline SearchStep 多查询并行

背景

Pipeline 模式 SearchStep 收到多个搜索查询时串行执行，导致搜索延迟随查询数线性增长。长文创作场景下查询数通常 3-5 个，延迟问题突出。

方案
  • 使用 sync.WaitGroup 并发执行多查询搜索
  • sync.Mutex 保护搜索结果切片的并发写入
  • 每个查询独立执行，结果合并后统一传入后续步骤
效果

搜索延迟从 O(n) 降为 O(1)（n 为查询数），3 查询场景延迟降低约 60%。

影响文件
steps.go (SearchStep.Execute)

D-05 前端

前端协作流表述优化与知识库数字脱敏

背景

个人中心偏好设置页的三种写作模式描述过于技术化，缺少场景引导。关于页面包含知识库文章具体数量（160+ 篇），不利于后续内容动态调整。

方案
  • 每种模式增加 scenario 字段，展示适用场景关键词
  • 提示信息从单段文本改为结构化分条，突出「最灵活 / 最稳定 / 最高质量」定位
  • 补充风格一致性说明（三引擎统一注入 RenderWritingConstraints）
  • 删除「160+ 篇」「预设评论风格」等具体数字和特定栏目名
  • 知识库描述改为「精选文章随时引用」
影响文件
settings-section.tsx about-section.tsx
D-06 暂缓

AutoFixStep 风格注入：暂不修改

背景

AutoFixStep.fixBody 在修正阶段缺少 RenderWritingConstraints 注入，存在风格漂移风险。

决策

暂不修改。原因：

  • 论文场景为边缘场景，商业版用户画像以短文创作为主
  • AutoFix 后有 PostReview² 再审机制兜底
  • 避免引入不必要的复杂性，待用户反馈后再评估
