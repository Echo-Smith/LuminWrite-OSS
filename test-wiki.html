架构对比
Pipeline（固定步骤流）
short_term_memory→ intent→ parallel_pre_write→ working_memory→ write→ post_review→ auto_fix→ memory_extract→ short_term_store

固定 9 步，每步独立 LLM 调用。审校和修正是强制步骤。Token 消耗最低，但 TTFT 受步骤数影响巨大（写作需跑完前 4 步才开始输出文章）。

Harness（LLM Agent Loop）
search_web→ search_web→ search_web→ write_article→ LLM 直接流式输出文章

LLM 在持续会话中自主选择工具。写作仅 4 步（3 次搜索 + 1 次 write_article 信号）。首字延迟极低（0.3-0.8s），因为 system prompt 后直接开始流式输出。每轮重发 system prompt，但 DeepSeek 磁盘缓存命中可覆盖 70%+。

工具集：search_web（搜索+LLM压缩）、read_source、write_article、review_article、revise_section、generate_outline

设计原理
为什么文章全文放 system prompt 而非 messages？
1. DeepSeek prompt caching 基于前缀匹配——system prompt 是每轮请求的前缀，放入文章全文使其成为缓存边界
2. messages 中的 assistant 回复如果携带完整文章，agent loop 每轮都会重复发送文章全文，token 暴涨
3. 用轻量摘要 [已输出文章 N 字，见当前文章全文] 替代，agent loop 可从 system prompt 获取文章上下文，messages 保持轻量

#问题类型建议

后续优化方向
1. 搜索压缩模型优化：当前用 V4 Pro + thinking=false 做压缩，可切换到更轻量的模型（如果有 Flash 版本）进一步降低压缩成本。
2. Harness 审校强制化：在 agent loop 结束后（LLM 停止调工具或 maxIterations 用完），如果文章已生成但未审校，强制执行一次 review_article。
3. Messages 裁切：agent loop 的 conversation 中，对早期 tool result 做摘要而非保留全文，进一步减少 token。
4. Chat 场景路由：IntentChat 时路由到 Pipeline 或 Harness 纯流式（无工具），避免 agent loop 的 token 开销。
